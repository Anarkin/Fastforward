# ARCHITECTURE

- Only what nothing else can express is recorded here: a rule a test, a lint rule or a tsconfig can check belongs there instead, its reason in the name of its test

## Folders

- What each folder holds and what may import what are the tests of `app/src/test/architecture.test.ts` and `app/src/test/components.test.ts`, with the lint rules and the tsconfigs keeping each side from importing the other
- A file holds one concept: split it along its concepts once it takes a second

## Decisions

- The i18n dictionary, `app/src/lib/shared/strings.ts`, holds whole sentences, never parts to join, to support localization and globalization
- A dialog names the names, paths, branches, hashes, URLs and keys it is about on lines of their own after a sentence without them, the rest naming them in their sentence
- The page is not trusted: the main process checks everything the page sends before it acts on it, as the page shows content from outside the app
- Each window is a `BrowserWindow` loading a page of its own, rather than windows opened from one page, so a window can close without the others and no page code needs to know which document it draws in
- A tab dragged out of its row is run by the main process, as Chrome runs it, rather than by HTML drag and drop, so a window follows the pointer and the tab shows in the row it is dragged over; the window the tab left is kept see-through rather than hidden until the drop, as hiding or closing the window the pointer was pressed in ended the drag, and Electron has no move loop of the system to hand the window to
- In the `zustand` stores of the page: a store holds every action that posts, streams included, and any batching of them; the component that makes a store reads as little of it as it can, leaving the rest to its children; selectors return the narrowest slice, a primitive or a stable reference, never a whole sub-state of which only part is used, collections built in the reducer; a component takes as props what differs between its uses or comes from its parent's own state, and reads the rest from the store, passing elements rather than props down, none through more than one component that doesn't use it; new memos only for an obvious cost, as a pass over a list or a parse, or an identity something depends on
- The cursor of the text box with the focus is drawn by the page beside it, anchored to it by CSS anchor positioning, so it follows the box wherever it moves, the box's own caret hidden, as Chromium draws a block caret under the character in the character's own color and has no width for its bar
- Every scrollbar is one of the browser, drawn by the one skin of `app/src/shell/page/window.css`, rather than drawn by the page, so it takes its strip from the layout and looks alike in every tool; the page lays a cover nothing sees over the scrollbar under the pointer and takes its presses itself, as the browser steps and jumps by pixels, knowing nothing of rows, gliding or snapping, and no page can keep it from a press on its own scrollbar; a view that scrolls by itself, as a file viewed, the terminal and a text scrolled sideways, stands a scroller of the browser in for its scrollbar, as many times longer than itself as the view is than what it shows, and no longer than where its thumb is at its shortest
- A control character is drawn by a font the app makes for the control characters alone, where it stands in the text, rather than left to the fonts of the system, as Chromium looks through them for each one, finds none and lays out a line of them 60 times slower, drawing a box, nothing or a gap as the fonts installed have it; nor swapped for the picture Unicode has for it, as VS Code does, as the editor, whose text CodeMirror draws, needed an element for each picture, and a file dense in them took longer to paint than to lay out; the font is made in the page as it starts, from the few dots of `app/src/shell/page/controlFontLetters.ts`, rather than shipped as a file, so its column is exactly as wide as a character of the monospace font of the settings, as Chromium cuts the size a font is scaled to with `size-adjust` to hundredths of a pixel, and 200 control characters ended most of a pixel off; it stands first among the fonts of the theme, covering the control characters and their pictures only, so no font of the user draws one another way; the form feed alone is swapped for its picture as its row is drawn, as Chromium draws it as nothing whatever font has it, copying giving it back, told from a picture the file itself holds by a mark on that picture
- A tooltip is drawn by the page, one card for the whole app that a notice is drawn as too, rather than the `title` of the browser, which takes no path, no key and no setting and is drawn by the system at a size of its own; an element tells its tooltip in attributes and listens for nothing, one watcher of the page finding the element under the pointer, so a row of a list costs nothing for its tooltip and what the page did not draw itself, as a Markdown file, has the same tooltip
- The app icon is drawn once, from the few numbers of `app/src/shell/page/appIconDrawing.ts`: the page draws it as an SVG for the device pixels it takes, as the browser puts an SVG on whole device pixels itself, and `npm run icons` renders every icon file of `app/build/` from it with a rasterizer of its own rather than a library, so each size puts the edges between the bands of the drawing on whole pixels and the disc is cut from the whole picture, no band drawn under another showing through its rim, and a test renders them again and compares their pixels, which are the same on every platform
- Use `oxlint` instead of `eslint`, because `typescript-eslint` does not support TypeScript 7 yet
- Use `shiki` with its Oniguruma engine, the TextMate grammars and engine VS Code uses, so scope rules carry over from VS Code; semantic tokens are left out, as they need a language server
- The colors of code are elements around its tokens, a line taking the color most of its tokens have so that only the others and the plain text between them need one, rather than ranges the browser colors through the CSS Custom Highlight API, as Chromium marks every range anew and paints every line that has one at each frame the page changes, which a list scrolled does at nearly every frame: a screen of a diff held 472 elements rather than 2,480, yet its wheel took 31.2 ms at its worst frames rather than 7.9
- The text of a file is to be drawn as cells on a canvas of the GPU, each glyph drawn once into an atlas and a screen of them in three draws, much as the terminal draws its screen, rather than as elements the browser lays out: first in the viewer, whose text and bytes have no elements any longer, then in the diff and the editor, the elements dropped as each follows; style, layout and paint were two thirds to four fifths of the main thread's work over the heavy files, and as cells the viewer took 2.5 ms at its worst frames over them rather than 7.8, the mean of its scenarios but opening, 9 of all 69 past the 5.5 ms of a frame at 180 Hz rather than 30, each of the 9 in the two files of wide characters never seen before, as a glyph takes a tenth of a millisecond the first time it is drawn
- A glyph of the cells is drawn by a canvas of the browser on the ground it stands on, in its color, and added to the screen as what it changed of that ground, so the subpixel edges of two glyphs that meet add up as the browser blends them, rather than cut out of its ground and laid over the screen, which dropped the edge of one where two met; by a canvas the GPU draws, as one the CPU draws was up to 8 levels off the text of the page; shifted by the part of a device pixel its text starts at, half a pixel at 125%, as Chromium draws text there; and with subpixel edges below 150% only, as Chromium draws scrolled text: a screen of cells is then the screen of elements to the pixel, but for the dots of spaces, a level off as the gradients that drew them dither, and a few dozen pixels where the edges of two glyphs meet
- The cells are drawn with WebGPU, the newer way a page draws with the GPU, rather than with WebGL, which the terminal draws with, taken from the start so the engine is never moved to it later, though a frame of three draws is no faster by it; the page has it only where Chromium trusts the GPU, and none drawn in software as WebGL is, so the tests of the cells start the app with the switches of `gpuWithoutOne`, which give the machines of CI, that have no GPU, WebGPU drawn in software, and the app shipped keeps to what Chromium allows
- A test learns what the cells show by asking their element, which tells the rows it shows with their text, their pieces of code and where each stands, where the frame draws a glyph and which spaces it dots, worked out only once asked, rather than from elements kept beside the canvas with the text of the rows, which every scroll would pay for, whose characters would stand where the browser lays them out rather than where the canvas draws them, and which drew marks of their own over the cells once; a screen reader is to get such a copy of its own once it is asked for, as `xterm.js` has one
- Markdown is rendered with `markdown-it`, which VS Code's preview uses too
- Mermaid diagrams in Markdown are drawn with `mermaid` on the page's main thread, as VS Code's preview draws them, since it measures text in the DOM and can't run in a worker
- PDFs are drawn with the viewer components of `pdfjs-dist` inside the page, not in an iframe; the page reads a PDF through PDF.js's range transport, as PDF.js asks for ranges itself only over HTTP

### Git, `git`

- Use the installed `git` CLI for everything, rather than a library or a git bundled with the app
- The commit list is kept whole by the main process per worktree, rather than read a page at a time as it scrolls, so the list knows its full size and locations can jump to any commit's position
- The bubbles of a commit with more than one are put on their lines by the page, from widths measured once in a hidden row of copies of the bubbles and the lanes of its row the main process counts as it walks the graph, rather than wrapped by the browser, so the list knows how tall a commit is before it loads or draws it and the height it scrolls through never changes as it draws them; the browser wrapped them only once drawn, and a commit with many bubbles grew the list as it came into view; as the room of a line changes, the commits drawn take their new lines at once and the others once it has rested 150 ms or the list scrolls, as laying out every commit at each step of the column dragged rendered the list at each step, 6.2 ms of main work a step against 4.5 ms in a list of 20,000 commits crowded with bubbles
- A viewer tab showing a file as git keeps a version of it saves the commit or the index and the file whose history it is beside its path, as the main process never reads the view of a tab; the viewer reads a copy git takes out of the blob, made anew whenever the tab shows, so a restart or a cleared cache loses nothing

### Commander, `commander`

- Folders are listed on Windows with `NtQueryDirectoryFile` through `koffi`, off the main thread, as Node can't read the hidden attribute or the size of files the system holds open, such as `pagefile.sys`
- Native calls go through `koffi`, COM interfaces too, called through their tables of functions, rather than an addon of our own, which would need a compiler and binaries built for each platform; the menu of Windows runs its own message loop on the main thread, as Explorer's does, so the app waits while it is open
- Folders that need an administrator are read by a helper, the app itself started elevated in a mode of its own, as Total Commander does, rather than by restarting the app elevated, which would elevate the shells and git too and cut off drag and drop with other windows
- Archives are read with the command line of 7-Zip, shipped with the app at a pinned version, rather than a library such as `@zip.js/zip.js` or `7z.dll` through `koffi`, as one program reads every format a file manager meets, alike on every platform, edits those it writes, and runs in a process of its own
- Flat view sorts and filters its files in a worker of the page, which hands back their order as indexes, as sorting millions of files on the page's main thread would stall every tool for seconds
- Duplicate files are hashed in worker threads of the main process, as hashing at the speed of an SSD, about 3 GB/s for SHA-256 on one core, would keep its main thread busy most of the time
- Folder sizes are counted in worker threads of the main process, each walking folders with blocking calls, as the main thread was busy 80 to 98% of a count through the lister, a count of `C:\Program Files` took 2.9 s rather than 0.8 s and one of `C:\Windows` 15.6 s rather than 8.8 s
- A row of the details is one element holding one text, rather than a cell for each column or a canvas: its name ends in a tab the side stops where the extensions start, the extension, size and date written out to the width of their columns, its generic icon is a background the page draws once in the muted color and the box of its mark no element, and a list that comes to rows of which it showed none writes them into the elements of those it left, as the browser styles, lays out and paints every element of every row anew at each step of a list dragged by its scrollbar, 10.5 ms a step of a folder of 20,000 files with ten elements a row and 4.4 ms with one, while a canvas would leave a screen reader no text and the page no row to point at or drag; a row keeps its cells only where one text can't show it, a name too long for its column or with characters of another width, a word the filter marks, the git icon of a repository, a size still counted

### Editor, `editor`

- The editor is CodeMirror 6, rather than Monaco or an editor of our own, as it draws its text in the DOM and lets decorations shape every part of it, so the text edited is laid out by the CSS and the code that lay out the diff and the viewer; Monaco measures and places every character itself, and an editor of our own would have to do the selection, input methods and undo again
- The code edited is colored by `shiki` in the worker of the colors, with the grammars of the viewer and the diff, rather than by CodeMirror's Lezer grammars, so the three color alike
- The text edited lives in the main process, as CodeMirror's `Text` with its undo history kept as JSON, as saving the settings reloads every page and a tab moves to another window by its id, so the page can't own it

### Terminal, `terminal`

- Use `xterm.js` with its WebGL renderer on the page and `node-pty` for the shells, as VS Code does
- The canvases of `xterm.js` take their CSS size from their size in device pixels, as it rounds that to whole CSS pixels, so the browser stretched them by a fraction of a pixel, blurring what they show further from their left edge
