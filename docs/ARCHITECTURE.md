# ARCHITECTURE

## Folders

```
app/src/
├─ boot/                           builds the owners below and wires Electron to them
├─ lib/{main,page,shared}          the library, code any owner may use, holding no state
├─ shell/{main,page,shared}        the frame the tools open in: windows, tabs, settings, storage
├─ tools/<id>/{main,page,shared}   a tool each, as the registries of the shell list them
└─ test/                           the tests
```

- Each owner, the library, the shell and each tool, keeps its code in three folders by where it runs: `main` in the main process, `page` in the page, and `shared` in both, holding only what both sides import, as the protocol between them
- What one side alone imports lives in the `main` or the `page` folder of its owner, what one owner alone uses in the folders of that owner, and what several use in the library
- Each folder builds on the ones below it, `boot` on the tools, the tools on the shell and the shell on the library: nothing imports `boot`, the library imports nothing from the others, no tool imports another, and the shell reaches the tools only through its registries
- `architecture.test.ts` checks these rules, and the lint rules and the tsconfigs keep each side from importing the other

## Decisions

- Put all text people read, logs included, in the i18n dictionary, `app/src/lib/shared/strings.ts`, as whole sentences, to support localization and globalization
- Set the names, paths, branches, hashes, URLs and keys in text people read apart in monospace through `lib/page/name`, never in quotes, as a name may hold quotes and a path broke at its hyphens: a dialog names them on lines of their own after a sentence without them, the rest in their sentence; a sentence keeps its names as parts of their own, from the main process to the page, and `plainOf` quotes them where nothing can be styled, as the log, a tooltip or a dialog of the system
- The page is not trusted: the main process checks everything the page sends before it acts on it, as the page shows content from outside the app
- Each window is a `BrowserWindow` loading a page of its own, rather than windows opened from one page, so a window can close without the others and no page code needs to know which document it draws in; the main process keeps which tabs each window holds, saved with the state, and each tool serves a page for each window, the active tab of its window, so a tab moves to another window by its id while its state stays in the main process, and a page acts only on the tabs of its own window
- A tab dragged out of its row is run by the main process, as Chrome runs it, rather than by HTML drag and drop, so a window follows the pointer and the tab shows in the row it is dragged over: the page that holds the pointer sends where it is, the main process moves the window the tab was torn into, kept loaded beforehand so it shows at once, finds the row under the pointer from where each page says its row is and which window is in front, and moves the tab into the window of that row while the pointer is over it, so that window shows the tab as it would once dropped, keeping the window the tab left, see-through rather than hidden, until the drop, even while it holds no tab, as hiding or closing the window the pointer was pressed in ended the drag; Electron has no move loop of the system to hand the window to, and on Wayland a window can neither place itself nor know where the pointer is, so tabs tear off nowhere there
- State that several components of the page share, state of the main process and state that outlives the component showing it live in a `zustand` store, at most one per tool and one for the shell, made where it mounts, handed out by one context that throws outside it once more than one component reads it, holding every action that posts, streams included, and any batching of them, and fed the main process's state messages through the existing reducers, replies to requests for pages or ranges staying with listeners; the component that makes a store reads as little of it as it can, leaving the rest to its children; selectors return the narrowest slice, a primitive or a stable reference, never a whole sub-state of which only part is used, collections built in the reducer; a component takes as props what differs between its uses or comes from its parent's own state, and reads the rest from the store, passing elements rather than props down, none through more than one component that doesn't use it; `lib/` holds no state, its components taking only props; other state one component uses stays in it; new memos only for an obvious cost, as a pass over a list or a parse, or an identity something depends on; so contexts don't stack and the logic is tested without React
- The cursor looks alike everywhere, by the `cursor` settings: `xterm.js` draws the terminal's, a layer of CodeMirror the editor's, and one controller of the page the cursor of the text box with the focus, beside it and anchored to it by CSS anchor positioning, so it follows the box wherever it moves, its own caret hidden, as Chromium draws a block caret under the character in the character's own color and has no width for its bar; the editor and the text boxes shape it by one function that fills the device pixels the WebGL renderer of `xterm.js` fills, a center on an edge at the left and the bottom as GL fills it, and a test compares the terminal and the editor with that function and a text box with the editor, pixel by pixel, at device pixel ratios of 1, 1.25, 1.5 and 1.75
- Use `oxlint` instead of `eslint`, because `typescript-eslint` does not support TypeScript 7 yet
- Use `shiki` with its Oniguruma engine, the TextMate grammars and engine VS Code uses, so scope rules carry over from VS Code; semantic tokens are left out, as they need a language server
- Lines are wrapped where Chromium would break them, as the diff lets the browser wrap them and the viewer wraps them itself: by Chromium's table between two characters of ASCII, and by ICU's line breaker beyond, asked through V8's `Intl.v8BreakIterator`, which also splits text into the characters it draws; the comparison of the two is a test, and without the iterator, as in Node, CJK characters and emoji break around them
- Markdown is rendered with `markdown-it`, which VS Code's preview uses too
- Mermaid diagrams in Markdown are drawn with `mermaid` on the page's main thread, as VS Code's preview draws them, since it measures text in the DOM and can't run in a worker
- PDFs are drawn with the viewer components of `pdfjs-dist` inside the page, not in an iframe; the page reads a PDF through PDF.js's range transport, as PDF.js asks for ranges itself only over HTTP, and runs no scripts, forms or editors of a PDF

### Git, `git`

- Use the installed `git` CLI for everything, rather than a library or a git bundled with the app
- The commit list is kept whole by the main process per worktree, rather than read a page at a time as it scrolls, so the list knows its full size and locations can jump to any commit's position

### Commander, `commander`

- Folders are listed on Windows with `NtQueryDirectoryFile` through `koffi`, a page of entries at a time off the main thread, as Node can't read the hidden attribute or the size of files the system holds open, such as `pagefile.sys`
- Native calls go through `koffi`, COM interfaces too, called through their tables of functions, rather than an addon of our own, which would need a compiler and binaries built for each platform; the menu of Windows runs its own message loop on the main thread, as Explorer's does, so the app waits while it is open
- Folders that need an administrator are read by a helper, the app itself started elevated in a mode of its own, as Total Commander does, rather than by restarting the app elevated, which would elevate the shells and git too and cut off drag and drop with other windows
- Archives are read with the command line of 7-Zip, shipped with the app at a pinned version, rather than a library such as `@zip.js/zip.js` or `7z.dll` through `koffi`, as one program reads every format a file manager meets, alike on every platform, edits those it writes, and runs in a process of its own; the commander reaches it only through a reader of archives of its own, so another can take its place
- Flat view reads the tree in the main process a few folders at a time and sends the page the files of each folder, and the page sorts and filters them in a worker of its own, which hands back their order as indexes, as sorting millions of files on the page's main thread would stall every tool for seconds
- Duplicate files are found by size first, which costs nothing, then by a SHA-256 hash of their first 64 KB and only then of the whole file, in four worker threads of the main process, as hashing at the speed of an SSD, about 3 GB/s for SHA-256 on one core, would keep its main thread busy most of the time; the hashes are kept by path, size and date while a side shows duplicates, so a change groups its files again without reading them
- Folder sizes are counted in four worker threads of the main process, each walking folders with blocking calls for 50 ms at a time and handing back the bytes and the folders it didn't reach, which are spread over the others, koffi loaded in them from where the app keeps it unpacked; the main thread was busy 80 to 98% of a count through the lister, a count of `C:\Program Files` took 2.9 s rather than 0.8 s and one of `C:\Windows` 15.6 s rather than 8.8 s

### Editor, in `commander`

- The editor is CodeMirror 6, rather than Monaco or an editor of our own, as it draws its text in the DOM and lets decorations shape every part of it, so the text edited is laid out by the CSS and the code that lay out the diff and the viewer: the font, the width of a character snapped to device pixels, the line height, the cells of emoji and wide characters, the `<wbr>` where Chromium would break and the hanging indent of wrapped lines; Monaco measures and places every character itself, and an editor of our own would have to do the selection, input methods and undo again; the cursor and selection are drawn by layers of our own, held within a row whose spaces hang past its edge, the cursor on its last cell as a terminal draws one past its last column
- The code edited is colored by `shiki` in the worker of the colors, with the grammars of the viewer and the diff, rather than by CodeMirror's Lezer grammars, so the three color alike; an edit colors again from its line to the first line whose state of the grammar is as it was, so typing colors a line or two
- The text edited lives in the main process, as CodeMirror's `Text` with its undo history kept as JSON, the page sending each change with the version it applies to and the main process checking it; saving the settings reloads every page and a tab moves to another window by its id, so the page can't own it, and closing a window or quitting saves its files from there
- A file is decoded into its text and marks, rather than into a text alone: its byte order mark, the line ending of each line that ends unlike most, and each run of bytes its encoding can't decode, kept as a placeholder with the bytes it stands for; the marks are mapped through each change and dropped from the ranges it replaces, so writing the text back gives the bytes read wherever nothing was edited, which tests of random files and random edits check
- A file is saved by writing a file of its own beside it and putting that in its place once whole, by `ReplaceFileW` through `koffi` on Windows, which keeps its attributes, its permissions and its streams, the Mark of the Web among them, and by a rename keeping its mode elsewhere; a file of several names, of another user or in a folder that lets no file be made is written in place, once its drive has room for it, as a replaced file would no longer be the one its other names reach
- A new file takes its line ending from its `.editorconfig`, else from the attributes and config of git, else from the editor section of the settings, which names its values as EditorConfig does

### Terminal, `terminal`

- Use `xterm.js` with its WebGL renderer on the page and `node-pty` for the shells, as VS Code does
- The canvases of `xterm.js` take their CSS size from their size in device pixels, as it rounds that to whole CSS pixels, so the browser stretched them by a fraction of a pixel, blurring what they show further from their left edge
- Run the shells in a utility process of their own, so a crash in the native code of `node-pty` or a flood of output can't stop or slow the window and the other tools
